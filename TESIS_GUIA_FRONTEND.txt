DESCRIPCIÓN DEL FRONTEND (MedAI) – TEXTO GUÍA PARA TESIS

Nota de uso:
Este texto está escrito para pegarse (con ajustes mínimos) en el capítulo/sección
de “Desarrollo/Implementación” o “Descripción de la aplicación”. Está enfocado
en el FRONTEND (interfaz web) y evita detalles de implementación a nivel de código.

------------------------------------------------------------------------------
1) Propósito y rol del frontend dentro del proyecto

El frontend de MedAI se desarrolló como una aplicación web orientada a facilitar
la interacción con el sistema de extracción de entidades clínicas. Su propósito
principal es ofrecer una interfaz simple y consistente para:

- ingresar notas clínicas (como texto o como documento),
- enviar la información al servicio de extracción,
- y visualizar los resultados de manera interpretable para revisión clínica.

En el contexto de la investigación, el frontend no se concibe como un entorno
de entrenamiento o experimentación del modelo, sino como una herramienta de
apoyo para uso operativo y validación: permite ejecutar el proceso de extracción
de forma controlada y revisar rápidamente qué entidades fueron identificadas.

------------------------------------------------------------------------------
2) Usuario objetivo y escenarios de uso

La interfaz está dirigida principalmente a:

- investigador(es) que necesiten ejecutar el extractor sobre múltiples notas,
- y/o personal clínico que requiera revisar de manera comprensible entidades
  detectadas dentro del texto.

Se contemplaron dos escenarios de uso principales:

1) Análisis de caso individual: cuando se requiere revisar con detalle una nota
   clínica específica y sus entidades extraídas.
2) Procesamiento por lotes: cuando se necesita ejecutar la extracción sobre
   múltiples documentos, optimizando tiempo y reduciendo pasos repetitivos.

------------------------------------------------------------------------------
3) Alcance funcional (qué hace y qué NO hace)

Qué hace el frontend:

- Permite cargar notas como texto pegado o como archivo.
- Solicita metadatos mínimos para trazabilidad (identificador del episodio y
  fecha/hora de la nota).
- Permite configurar parámetros generales de extracción antes de procesar notas.
- Presenta los resultados en vistas diseñadas para revisión (texto resaltado y
  resumen organizado por tipo de entidad).
- Proporciona una “leyenda” o referencia de entidades para apoyar la interpretación.

Qué NO hace el frontend (por decisión de diseño):

- No ejecuta el modelo de extracción en el navegador.
- No reemplaza al backend ni sus procesos de persistencia.
- No está pensado para almacenar información clínica de forma local más allá
  de la interacción necesaria durante el uso de la interfaz.

------------------------------------------------------------------------------
4) Estructura general: en qué se centra la app

La aplicación se centra en un flujo único y claro:

   Cargar información clínica  →  Ejecutar extracción  →  Revisar resultados

Para soportar ese flujo, el frontend se organizó en superficies de interacción
que el usuario identifica de manera natural:

a) Área de carga y envío:
   - Caso individual: entrada de texto o carga de un archivo (excluyentes).
   - Carga múltiple: selección de varios archivos y registro de metadatos por archivo.

b) Área de configuración:
   - Un panel lateral de ajustes permite seleccionar opciones generales que se
     aplican por defecto a las extracciones (por ejemplo, la familia de modelo; en la versión actual la variante se aplica automáticamente).

c) Área de resultados:
   - Vista de texto con resaltado de entidades (para validar contexto).
   - Vista en lista, agrupada por categorías de entidad (para revisión rápida).

d) Área de apoyo a interpretación:
   - Una leyenda de entidades presenta el significado clínico de las categorías
     reconocidas, junto con un color asociado para mantener consistencia visual.

------------------------------------------------------------------------------
5) Cobertura clínica (categorías de entidades representadas)

La interfaz se diseñó para representar entidades propias del contexto de
ventilación mecánica y variables clínicas asociadas. De forma general, el
frontend puede mostrar categorías relacionadas con:

- configuración ventilatoria (modo, FiO2, PEEP, FR, VT, etc.),
- monitoreo ventilatorio (saturación, presiones relacionadas),
- signos vitales y hemodinámica,
- variables antropométricas (edad, peso, talla),
- resultados de gases arteriales (pH, PaCO2, HCO3, PaO2, etc.),
- y diagnóstico, como entidad clínica de alta variabilidad semántica.

Esta cobertura se muestra al usuario mediante una leyenda de entidades y un
esquema de colores consistente entre la referencia y la visualización de resultados.

------------------------------------------------------------------------------
6) Flujo de interacción con el backend (nivel conceptual)

El frontend opera como cliente del servicio de extracción. De manera conceptual:

1) El usuario ingresa la nota (texto o archivo) y metadatos mínimos.
2) El frontend envía la solicitud al backend (servicio de extracción).
3) El backend procesa la nota y responde con un identificador de resultado.
4) El frontend consulta el resultado y lo presenta en pantalla para revisión.

Para el caso de procesamiento por lotes:

1) El usuario carga múltiples archivos.
2) La interfaz solicita metadatos por archivo (episodio, fecha/hora).
3) Se envía el lote al backend para procesamiento.
4) Se muestra un resumen por archivo (procesado / error) y, cuando es posible,
   un acceso directo a la vista de resultados de cada nota.

En una tesis, este flujo puede representarse con un diagrama simple de
secuencia (Usuario → Frontend → Backend → Frontend) o con un diagrama de
arquitectura de alto nivel (Cliente web ↔ API de extracción).

------------------------------------------------------------------------------
7) Decisiones de diseño de interfaz (por qué se ve y se usa así)

Las decisiones de diseño se centraron en usabilidad y revisión clínica:

- Separación en dos modalidades (individual/lote) para cubrir escenarios reales.
- Paneles laterales para configuración y referencia, evitando sacar al usuario
  del flujo principal.
- Visualización dual de resultados:
  - texto resaltado para revisar contexto y exactitud,
  - lista agrupada para revisión rápida por categoría.
- Retroalimentación constante (carga/progreso/errores) para evitar incertidumbre
  durante operaciones que pueden tardar (por ejemplo, procesamiento de archivos).
- Lenguaje de interfaz en español para coherencia con el dominio y los usuarios.

------------------------------------------------------------------------------
8) Manejo de errores y estados de carga (robustez operativa)

Se incorporaron mecanismos de robustez en la experiencia de usuario:

- Validación de campos obligatorios (metadatos mínimos antes de procesar).
- Restricciones de entrada (evitar enviar simultáneamente texto y archivo).
- Mensajes claros ante fallas de conexión, archivos no válidos o errores de servidor.
- Indicadores de “cargando/procesando” que bloquean acciones para prevenir
  envíos duplicados y mantener consistencia del flujo.

Esto es importante en un entorno clínico/investigativo, donde el usuario debe
entender rápidamente si la operación está en curso, si finalizó o si requiere
corrección de datos.

------------------------------------------------------------------------------
9) Despliegue del frontend (Vercel)

El frontend fue desplegado en Vercel, lo que permitió:

- publicar la aplicación como una URL accesible desde navegador,
- y manejar variables de entorno para conectar con el backend correspondiente.

Con base en la evidencia disponible en el repositorio, se puede sustentar la URL pública y el uso de variables de entorno. Si se desea afirmar autodespliegue o previsualizaciones, conviene anexar evidencia directa desde la configuración de Vercel.

Esta estrategia facilita la demostración del sistema en contextos académicos y
la iteración rápida durante el desarrollo, manteniendo una separación clara
entre interfaz (frontend) y procesamiento (backend).

Referencia del despliegue del frontend:
https://medai-frontend-seven.vercel.app/

11) Texto corto tipo “resumen ejecutivo” (por si lo necesitas)

Se implementó un frontend web para MedAI con el objetivo de facilitar la carga
de notas clínicas y la revisión de entidades extraídas por el sistema. La
aplicación soporta un flujo de caso individual y un flujo de procesamiento por
lotes, solicitando metadatos mínimos para trazabilidad. Los resultados se
presentan mediante una vista de texto resaltado y una lista organizada por tipo
de entidad, complementadas por una leyenda de categorías. El frontend se
desplegó en Vercel, permitiendo acceso vía navegador y actualizaciones
controladas del sistema.
